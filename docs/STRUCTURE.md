# 構造の理由

この文書は、Poker GTO がいまの形になっている理由をまとめたもの。画面の組み立て、壁打ちの流れ、解説の並べ方、コードの分け方のそれぞれについて、作り手（Claude）がどう考えてその構造を選んだかを書く。

`DESIGN.md` は「いまの決まりごと」、`DESIGN_LOG.md` は「決まりごとに至ったやり取り」を残している。この文書はその間をつなぐ。決まりごとが、どんな考えから来た構造として形になっているかを、構造ごとに説明する。

書き方の約束は `DESIGN_LOG.md` と同じにする。書くのは、作り手が実際に考えた理由と、使う人がどう感じるかについての想定、そして選ばなかった案だけにする。選ばなかった案を残すのは、あとで「こうしたほうが簡単では」と同じ案に戻ってしまわないようにするためだ。

---

## 1. 入り口は「分析・壁打ち・教材」の3つ

**考えたこと**: 人は、機能を探しにアプリを開くわけではない。「このハンド、どうすべきだった？」「腕を試したい」「仕組みを知りたい」という目的を持って開く。そこで、入り口を目的の数だけにした。

**使う人についての想定**: 入り口が多いと、開くたびに「どこへ行けばいいか」を考えさせられる。勉強を始める前に頭を使わせると、開くこと自体が面倒になる。

**選ばなかった案**: 左にバーを置き、レンジ表・計算機・ソルバー・ドリルを並べる案。最初はこの形だった。作る側には整理されて見えるが、使う側には「どれが自分のやりたいことか」が分からなかった。

## 2. 画面は「左に卓、右にドック」で、スクロールさせない

**考えたこと**: 分析でも壁打ちでも、主役は卓の上の1手だ。答えやレンジは、その1手を判断するための材料にあたる。そこで、主役の卓を左に大きく置き、材料は右のドックにタブで重ねた。どちらも窓の中に収め、答えを見るためにスクロールしなくて済むようにしている。

**使う人についての想定**: スクロールは、手の流れを切る。1問ごとに下へ答えを見に行き、上へ戻って次の問題を押す動きは、10問やると疲れになる。「スクロールが煩わしい」と言われたのは、この疲れのことだと受け取った。

**選ばなかった案**: 卓の下に答えとレンジを縦に積む案。情報は全部見えるが、目と手の往復が増える。

## 3. 操作はすべて卓の上

**考えたこと**: ポーカーをしたことのある人は、オンラインのポーカーで「卓・席・手札・下に並ぶボタン」という並びに慣れている。その文法をそのまま借りれば、説明がなくても操作が分かる。Fold と Call を左に置き、レイズはまとまった枠に入れて額を選ばせる並びも、ポーカーのクライアントと同じにした。

**使う人についての想定**: 学ぶ場所と使う場所の見た目が近いほど、学んだことを実戦で思い出しやすい。

**選ばなかった案**: フォームに席やアクションを入力する案。入力の正確さは同じでも、ゲームとしての手触りがなくなる。

## 4. 壁打ちは「1問 → 採点 → 次へ」を、10問で1ラウンドにする

**考えたこと**: 1問で終わる練習は、終わりが見えないので、やめどきも続けどきもない。10問を1ラウンドにして結果（S〜C）を出すと、「あと3問でラウンドが終わる」という小さな目標が生まれる。ランクと経験値は、ラウンドをまたいだ伸びを見せるために置いた。外しても経験値が少し入るのは、間違いを罰にしないためだ。

**使う人についての想定**: ネットの感想を見ると、Steam のポーカーゲームでは「短い時間で遊べる」「始めるまでの壁が低い」ことが褒められていた。一方で、進み具合が消える不具合は強く嫌われていた。そこで、1ラウンドを数分で終わる長さにし、成績はブラウザに残して、読み込みに失敗しても壊れないようにしている。

**選ばなかった案**: 時間制限を付ける案。練習アプリの感想には、制限時間を外せないことへの不満があった。ゆっくり考えたい人がいるので、このアプリでは時間で急かさない。

## 5. 採点のあとは「評価 → 頻度 → 覚え方 → 解説」の順に見せる

**考えたこと**: 答えた直後の人がまず知りたいのは「合っていたか」で、次が「GTO はどうするか」だ。そこで評価を判のように大きく出し、その下に頻度のバーを置いた。その次に「覚え方」の一言を置いて、解説はいちばん下にしている。

**使う人についての想定**: 解説を最後まで読む人ばかりではない。急いでいる人も、覚え方の一言だけは目に入るようにしたかった。覚え方を解説の最後に置いた版では、カードの下に隠れて読まれなかった。

### 覚え方を言葉にした理由

GTO の頻度は「Raise 72.4%、Fold 27.6%」のように細かい。練習アプリの要望には、「細かい頻度は実戦で使えず、覚えられない」という声があった。そこで頻度を「いつも（90% 以上）」「たいてい（60% 以上）」「半分ほど（40% 以上）」「ときどき（10% 以上）」の4つの言葉に丸め、「CO の A5s は、たいてい Raise、ときどき Fold」という一文にしている。10% 未満のアクションは入れない。卓で毎回思い出すには、主な選択だけで足りるからだ。

**選ばなかった案**: 頻度そのものを丸めて採点にも使う案。採点まで丸めると、ソルバーの答えとずれる。丸めるのは覚えるための言葉だけにして、採点は元の頻度のままにした。

## 6. 解説は「場面 → 手札 → 結論」の順に並べる

**考えたこと**: 人がポーカーで判断するときは、だいたい次の順に考える。

1. どんな場面か（誰がレイズしたか、いくら払えば続けられるか、後ろに何人いるか）
2. 自分の手はどういう手か（スーテッドか、キッカーは強いか、相手のレンジにどれだけ勝てるか）
3. だからどうするか

前の版の解説は、理由を思いついた順に並べていた。中身は正しくても、読む人が頭の中で並べ直す必要があった。そこで解説の1行ずつに「場面」「手札」「結論」の印を持たせ、表示するときにこの順に並べ替えるようにした。コードでは `src/trainer/explain.ts` の `Reason` と `inThinkingOrder` がこれにあたる。

どの手札にも「手札」の行を必ず1行付けるようにした。正解が Fold の手でも、人は「この手はなぜ弱いのか」を確かめたいからだ。たとえば 65o は、キッカーが弱いから降りる手ではない。つながっていてストレートの見込みはあるが、オフスートでペアも低い。理由の言い方を手札の形に合わせている。

**使う人についての想定**: 練習アプリの感想で一番多かった不満は、「なぜその手なのかの説明が薄く、学びにならない」だった。初心者には、UTG のような席の名前の説明もないと言われていた。

**選ばなかった案**: 解説の文を長くして、全部を1段落で語る案。情報は増えるが、どこに何が書いてあるかが分からなくなる。

### 用語には説明を添える

解説の中の UTG・EQR・ドミネート・ブロッカーなどの用語には点線を引き、カーソルを重ねると短い説明が出るようにした（`src/learn/glossary.ts`）。初めての人が、解説の途中で用語を調べに行って流れが切れないようにするためだ。

### 選んだ額で呼ぶ

額を選んでレイズしたときは、解説の「選んだ〜」の文を、選んだ額で書く。データの額（3Bet 11bb）のまま「選んだ 3Bet 11bb は」と書くと、6.5bb を選んだ人には別の手の話に読めるからだ。覚え方の一言だけは GTO の額のままにしている。覚えてほしいのは GTO の額だからだ。

## 7. 間違えた問題は、あとで出し直す

**考えたこと**: 人が覚えるのは、間違えた問題に少し時間をおいてもう一度答えたときだ。そこで、間違えた場面と手札を残し、「間違えた問題」として出し直せるようにした。正解すると候補から外れる。

**使う人についての想定**: 練習アプリの感想には「練習する場面を絞れない」「出題が一部の場面ばかりになる」という不満もあった。このアプリでは、出題の種類（オープン、オープンへの対応、3ベットへの対応など）と自分の席を選べる。間違えた問題も、その選択肢の1つとして並べている。

## 8. できないことは、できるように見せない

**考えたこと**: プリフロップのデータは、ソルバーで解いた答えではなく、6人卓をもとにした近似値だ。1つの場面に1つのレイズ額しか持たない。そこで、データにない額を選んだときは「データにないサイズなので、GTO の額として続けています」と出す。分析のコールの EV には「オールインなら」という前提を添え、実際は EQ を取りこぼすぶんだけ下がると書いている。

**使う人についての想定**: 練習アプリの感想で強く嫌われていたのは、「チャートと採点が食い違う」ことだった。答えの根拠が信用できなくなると、そのアプリでの練習全部が疑わしくなる。分からないことを分からないと示すほうが、信頼を保てる。

## 9. コードの分け方

```
src/poker/     ポーカーの計算だけ（カード、勝率、必要勝率、ベットの額）。画面を知らない
src/trainer/   壁打ちの規則（採点、解説、成績、ラウンド、復習）。画面を知らない
src/learn/     教材の章と用語集
src/components 卓・ボタン・メーターなどの部品
src/pages/     3つの入り口の画面。上の部品と規則を組み合わせる
solver/        ポストフロップのソルバー（Rust）。ローカルのサーバーとして動く
```

**考えたこと**: 計算と規則を、画面から切り離した。採点や解説の正しさは、ブラウザを開かなくてもテストで確かめたいからだ。解説の順番や覚え方の言葉も `src/trainer/explain.ts` の関数として書き、テスト名で「何を保証するか」を読めるようにしている。画面を作り直すことはこれまで何度もあったが、そのたびに計算と規則には手を入れずに済んだ。

**選ばなかった案**: 画面の部品の中で採点や解説を組み立てる案。最初は書くのが速いが、画面を変えるたびに規則まで壊れる。
